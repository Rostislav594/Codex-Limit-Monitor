# Codex App Server protocol notes

Verified on 2026-08-11 during Stage 0 of Codex Limit Monitor development.

## Environment

- Windows: win-x64
- Codex CLI: `codex-cli 0.147.0`
- App Server transport: `stdio://` (JSONL, one JSON object per line)
- .NET SDK available for later stages: `10.0.302`
- Generated protocol schema command:

  ```powershell
  codex app-server generate-json-schema --out <directory> --experimental
  ```

The generated schema is the compatibility authority for the locally installed
Codex version. The App Server command and schema generator are currently marked
experimental, so protocol handling must remain isolated from the UI and tolerate
compatible optional-field additions.

## Verified initialization sequence

The following sequence succeeded against the local App Server:

1. Start `codex app-server --stdio`.
2. Send an `initialize` request with `clientInfo` and capabilities.
3. Receive an initialization result containing `codexHome`, `platformFamily`,
   `platformOs`, and `userAgent`.
4. Send the `initialized` notification.
5. Send `account/read`.
6. Send `account/rateLimits/read`.

Minimal request shapes:

```json
{"method":"initialize","id":1,"params":{"clientInfo":{"name":"codex-limit-monitor","title":"Codex Limit Monitor","version":"0.1.0"},"capabilities":{"experimentalApi":true}}}
{"method":"initialized"}
{"method":"account/read","id":2,"params":{"refreshToken":false}}
{"method":"account/rateLimits/read","id":3}
```

The probe intentionally omitted a `jsonrpc` property because that is the shape
generated by the installed App Server schema. Request IDs must still be treated
as opaque correlation values by the application.

## Verified rate-limit response shape

The live response contained these top-level result fields:

- `rateLimits`: backward-compatible single-snapshot view.
- `rateLimitsByLimitId`: multi-snapshot view keyed by a metered limit ID.
- `rateLimitResetCredits`: optional reset-credit information that the MVP must
  ignore safely. The application must never attempt to consume reset credits.

The live account returned:

- one entry in `rateLimitsByLimitId`;
- a populated `primary` window;
- no `secondary` window.

No real percentage, reset timestamp, credit balance, email address, or token was
written to this repository.

A rate-limit snapshot can currently contain:

- `limitId` and `limitName`;
- `planType`;
- nullable `primary` and `secondary` windows;
- `rateLimitReachedType`;
- `credits`;
- `individualLimit`;
- nullable `spendControlReached`.

Each rate-limit window contains an integer `usedPercent` plus nullable
`windowDurationMins` and `resetsAt` values. Remaining percentage is a derived UI
value and must be clamped to the range 0 through 100.

## Update semantics

`account/rateLimits/updated` is present in the generated server-notification
schema. Its payload is explicitly documented as a sparse rolling update.
Missing or nullable account metadata in this notification does not clear a
previously observed value. The client must merge the update into the latest full
snapshot or perform another `account/rateLimits/read`.

The short Stage 0 probe did not wait for real usage to change, so notification
delivery was schema-confirmed rather than force-triggered. The integration test
server in Stage 2 must cover notifications arriving before, during, and after a
request/response exchange.

## Implementation consequences

1. Treat `rateLimitsByLimitId` as the preferred multi-limit source when present;
   retain `rateLimits` as the compatibility fallback.
2. Do not assume that `primary` and `secondary` both exist or correspond to fixed
   five-hour and weekly labels.
3. Flatten snapshots into display buckets using stable identities composed from
   the metered limit ID and window role, while deriving friendly labels from
   `limitName` and `windowDurationMins`.
4. Keep DTOs forward-compatible and make optional fields nullable.
5. Keep stdout exclusively for JSONL protocol messages and stderr exclusively
   for sanitized diagnostics.
6. Never log the `account/read` email, authentication payloads, credit balance,
   real usage percentages, or reset timestamps by default.
7. After reconnecting, always perform initialization and a new full read before
   applying rolling updates.

Passed. Real rate-limit data can be obtained through the supported local App
